## Usage

```tsx
import { emailProfile, type EditorEmailBlock } from '@zeroxsolutions/editor-core/profiles/index';
import { createEmailRenderer } from '@zeroxsolutions/editor-core/template/email/index';

import { EmailEditor } from '@/components/editor/profiles/email/email-editor';
```

```tsx
const profile = emailProfile({
  variables: [
    { name: 'first_name', type: 'string', label: 'first name', sampleValue: 'Lan' },
    { name: 'account_url', type: 'url', label: 'account link', sampleValue: 'https://example.com/account' },
  ],
});
const renderer = createEmailRenderer({ theme });

function WelcomeEmail({ blocks, save }: { blocks: EditorEmailBlock[]; save: (blocks: EditorEmailBlock[]) => void }) {
  return (
    <EmailEditor
      label="Email body"
      profile={profile}
      value={blocks}
      onChange={save}
      renderer={renderer}
      previewInput={{ subject: 'Welcome', preheader: null, locale: 'en', layoutProps }}
      sender="Example"
    />
  );
}
```

The editor offers the Document Editor's paragraph, bulleted list, callout, code block, divider, button, columns,
heading, quote, image and table, and the email's HTML block and the library's hero, card, social links, spacer
and legal footer. Click a block's grip, or press Mod-/, to open its block menu. The menu holds Turn into,
Duplicate and Delete, and the block's own settings, such as Align, Space after, Tone, Width, Level, Lanes, Link,
Height or Size.

The editor is drawn as the Document Editor is, with its toolbar above the blocks and nothing around them.
With a `renderer`, an Edit and a Preview tab sit at the end of the toolbar's row, as a Mermaid block's switch
does. The Preview tab shows the rendered email with each variable's `sampleValue`, and the toolbar's row holds
only the tabs while it is open. `layoutProps` is the default layout's logo and footer, and the demo's source
defines it.

The preview heads the email as a mail client heads an open message: the subject, then the `sender` and the
preheader, over a hairline. The email follows edge to edge, with its own background the only surface. It is
drawn at the editor's own width, so under 600px the default layout goes full-bleed, with no gutter or border
around its card, and in the theme around the editor: inside a `.dark` scope its `prefers-color-scheme: dark`
rules apply, and a theme switched later redraws it. Pick a device and the dark theme on the bar above the demo
to see both.

## Text styling

<ComponentPreview name="email-editor-text-styling-demo" />

The bubble aligns the selection's paragraphs to the start, the centre or the end, and colours its text and its
background from the same tokens as the [Document Editor](/docs/editor/document-editor#text-styling); the block
menu's Turn into makes a paragraph Lead or Small text. There is no justify, which mail clients draw unevenly.
The wire stores a paragraph's `align` as `left`, `center` or `right` and its `size` as `lead` or `small`, and a
coloured run in the text as `{color=red}...{/color}` or `{bg=amber}...{/bg}`. The renderer draws each hue from the
theme's `colors.hues`, and `accent` from `colors.accent`, in the light palette and the dark one; a product that
names none gets the defaults.

An image is aligned and resized in the email too, columns are weighed and a section is set on a background,
within what an email can draw: [Editor Layout](/docs/editor/editor-layout#in-an-email) shows it.

## Library blocks

| Block         | Holds                                                                                                                                                     |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `heading`     | a title at level 1, 2 or 3, level 2 when it names none                                                                                                    |
| `quote`       | words set off by a rule at their left, in the muted colour                                                                                                |
| `image`       | a hosted `https:` image, its required alt text, a caption and a link, never wider than where it sits                                                      |
| `table`       | rows of short text, the first one headers where `header` is set, at most 20 rows of 6 columns                                                             |
| `hero`        | a wide image and its alt text, a heading, text, and a button, left or centred                                                                             |
| `card`        | the hero's fields in a frame                                                                                                                              |
| `socialLinks` | 1 to 8 icon links, each a label, a hosted icon your product supplies and a link, left, centred or right                                                   |
| `spacer`      | empty space, small, medium or large                                                                                                                       |
| `legalFooter` | who sends the mail, why the reader gets it, the required postal address, and the required unsubscribe link, worded by `unsubscribeLabel`, left or centred |

A hero's and a card's button is drawn only with both its label and its link, and the write check refuses one
without the other. An image, a hero's and a card's image are drawn at most at the width they sit in (566px, the
card's width less its border and padding, a lane's width, or a section's inside its padding), since Outlook on
Windows reads no `max-width` and would push the card wider. A hero, a card and the social links take `https:` images only. A lane holds no hero or
card, which are drawn at the card's whole width. The card is also a block for the Document Editor: `card` from
`@zeroxsolutions/editor-core/blocks/index` is one definition for both editors. The email editor holds it already,
so it goes in neither `emailProfile`'s `blocks` nor the editor's, which throw for it. In a table cell the editor keeps
to a line of text, since the email writes each cell as one.

`MAIL_LAYOUT_KINDS` is the `allow` of a mail layout's header and footer regions: paragraph, list, callout,
divider, columns and the legal footer, so the sender's address and the unsubscribe link can live once in the
footer every mail of a product shares. [Block Library](/docs/editor/block-library) lists these blocks beside the
Document Editor's. The demo above opens on a hero and ends on a card, a spacer, social links and the legal footer.

## Theme

`createEmailRenderer` takes the `EmailTheme` every default block and the default layout paint with. Mail
clients read no CSS variable and no `oklch()`, so each color is a six- or eight-digit hex.

```tsx
import { createEmailRenderer, type EmailTheme } from '@zeroxsolutions/editor-core/template/email/index';

const theme: EmailTheme = {
  colors: {
    background: '#FFFFFF',
    foreground: '#09090B',
    primary: '#007A55',
    primaryForeground: '#ECFDF5',
    muted: '#F4F4F5',
    mutedForeground: '#63636D',
    border: '#E4E4E7',
  },
  dark: {
    background: '#0A0A0A',
    foreground: '#FAFAFA',
    primary: '#00BC7D',
    primaryForeground: '#022C22',
    muted: '#262626',
    mutedForeground: '#A1A1A1',
    border: '#262626',
  },
  radius: 10,
  font: { family: 'Inter', fallback: 'Arial, Helvetica, sans-serif' },
};

const renderer = createEmailRenderer({ theme });
```

`dark` is optional and takes the same keys as `colors`. With it, the email declares a light and a dark color
scheme, and a client in dark mode that reads `prefers-color-scheme`, such as Apple Mail, paints it with `dark`.
Gmail reads no such rule and shows the light palette. Without `dark`, the email declares no dark scheme and
stays light. `radius` is in px. `createEmailRenderer` throws `EmailThemeInvalid`, naming the value's path,
for a color that is not hex or a font list that holds anything but names, spaces, commas, hyphens and single
quotes.

Hand the blocks `onChange` gives you back as `value`, and the editor does not reload them. After a save,
call `editor.run('assignBlockIds', { ids })` on the editor `onReady` gave you, with a map of block key to
saved id. The blocks it reports from then on carry those ids.

## Styling

The renderer draws the email from tables, each part carrying a class, and inlines a base stylesheet built
from the theme into each element's `style`, since some clients drop a `<style>` block or parts of it. `css`
adds your own sheets after the base one. At equal specificity a rule of yours wins by coming later.

```tsx
const renderer = createEmailRenderer({
  theme,
  css: `
    .zx-callout { border-color: #007A55; }
    @media (prefers-color-scheme: dark) {
      .zx-callout { border-color: #00BC7D; }
    }
  `,
});
```

An inlined rule's selector is made of classes only: `.a`, `.a.b`, `.a .b` and `.a > .b`. A tag, an id, an
attribute, a pseudo-class or `*` throws `EmailStylesheetInvalid`, which names the sheet's index, the line, the
column and the reason. So do `@import`, a `var()` with no value and CSS that does not parse. `var()` reads the
custom properties of a top-level `:root` or `.zx-root` rule and is resolved before the value is inlined.

Your `@media` and `@supports` rules hold in a query, so they cannot be inlined. For each query the renderer
computes every element's style as a browser would while the query holds: your top-level rules, the rules of
each query around it and its own, by importance, specificity and order, with the custom properties those
queries' `:root` redefine. The element gets one class of its own for the query, such as `zx-q0-3`, and the head
gets, under the query, each declaration that differs from the inlined style and each one the query's rules set,
made `!important`. The class is written once more than the classes of the base sheet's widest rule, as in
`.zx-q0-3.zx-q0-3.zx-q0-3`, so your query's style beats the base sheet's dark and narrow-screen rules on that
element, even where it keeps the inlined value, such as a light colour kept in dark mode:

```css
@media (prefers-color-scheme: dark) {
  .zx-callout {
    background: #f4f4f5;
  }
}
```

When two of your queries hold at once, a property both set on one element is decided by their order in your
sheet, not by selector specificity: the later query wins. A nested query is computed with the rules of the
queries around it, so inside it the cascade is a browser's. A selector in a query that is not class-only, such
as `.zx-button:hover` or `p`, is kept in the head, made `!important`, as is a query inside another at-rule, such
as `@layer`. The renderer cannot compute such a rule, so where its last part has a class, that class is repeated
as often as a query class is, and the rule wins over the computed style on an element both select, whatever
their specificity in your sheet; one with no class there, such as `p`, does not. A `:root` in a query holds custom properties only; a declaration there throws, as it does at the top.

An inlined `!important` decides the cascade among your rules but is not written into the `style`, since there it
would beat the head's dark and narrow-screen rules; `stylesheetWarnings` names each one as `important-dropped`.

| Class                                                     | On                                                       |
| --------------------------------------------------------- | -------------------------------------------------------- |
| `zx-body`, `zx-canvas`, `zx-card`, `zx-inner`             | the body, the background table, the card and its padding |
| `zx-region-header`, `zx-region-body`, `zx-region-footer`  | each region's blocks                                     |
| `zx-block`, `zx-block-<type>`                             | each block's row, by its type                            |
| `zx-align-<align>`, `zx-space-<spaceAfter>`               | the row, by the block's `align` and `spaceAfter`         |
| `zx-text`, `zx-tone-muted`, `zx-link`                     | a paragraph's text, its muted tone, a link in text       |
| `zx-callout`, `zx-code`, `zx-list`, `zx-divider`          | the callout, code, list and divider blocks               |
| `zx-heading`, `zx-heading-<level>`, `zx-quote`            | a heading, by its level, and the quote                   |
| `zx-image-fluid`, `zx-caption`                            | an image that shrinks to the screen, and its caption     |
| `zx-table`, `zx-table-cell`, `zx-table-head`              | the table, each cell, and the header row's cells         |
| `zx-hero-<part>`, `zx-card-block`, `zx-card-block-<part>` | a hero's and a card's image, heading, text and action    |
| `zx-icons`, `zx-icon`, `zx-icon-image`                    | the social links' row, each link's cell and its icon     |
| `zx-spacer`, `zx-legal`, `zx-legal-text`                  | the spacer, and the legal footer and each of its lines   |
| `zx-button`, `zx-width-full`                              | the button, and a full-width one                         |
| `zx-lane`, `zx-lane-last`                                 | each lane of a columns block, and the last               |
| `zx-footer`, `zx-footer-line`                             | the default layout's footer and each of its lines        |

Some CSS reaches only some inboxes: `display: flex` and `grid`, `position`, `float`, `transform`,
`oklch()` and the other new color functions, and gradients. For each declaration of yours that uses one,
`renderer.stylesheetWarnings` holds its place, the feature's name on [caniemail.com](https://www.caniemail.com),
and the clients that drop it. `checkEmailRenderer` reports them too, so a test fails on them.

## Your own blocks

`defineEmailBlock` declares a block once, for the renderer and for the editor. Its fields are what the author
writes, its attributes what the author picks, and its `render` draws it with the renderer's primitives.

```tsx
import {
  choice,
  createEmailRenderer,
  defineEmailBlock,
  plainText,
  richText,
} from '@zeroxsolutions/editor-core/template/email/index';

const testimonial = defineEmailBlock({
  type: 'testimonial',
  label: 'Testimonial',
  fields: { text: richText(), author: plainText({ max: 120 }) },
  attributes: { tone: choice(['neutral', 'brand'], 'neutral') },
  render: ({ fields, attributes }, h) =>
    h.section({ class: ['zx-testimonial', `zx-testimonial-${attributes.tone}`] }, [
      h.text({ markup: fields.text }),
      h.text({ class: 'zx-testimonial-author', text: fields.author }),
    ]),
  sample: {
    fields: { text: '{{first_name}} set us up in a day.', author: 'Lan' },
    variableTypes: { first_name: 'string' },
  },
});

const renderer = createEmailRenderer({
  theme,
  css: '.zx-testimonial { border-left: 3px solid #E4E4E7; }',
  extraBlocks: [testimonial],
});
```

```tsx
const profile = emailProfile({ variables, blocks: [testimonial] });

<EmailEditor profile={profile} blocks={[testimonial]} renderer={renderer} /* ... */ />;
```

`emailProfile`'s `blocks` adds the type to the profile's kinds, and `validate` checks each field as the
renderer will: an empty body, a field over its `max`, and a link or image address it would refuse. `EmailEditor`'s
`blocks` offers the block in the slash menu and exports it, and throws `EditorError` for a block the profile does
not hold through its `blocks`. A lanes block holding fewer or more lanes than it takes is a `lanes-count`, and the renderer draws
no lane past its `max`. The rich text
field and each plain field are edited in place, with no caption. A link opens from a link icon on the block, and an
image from the image itself, in a popover that offers the `url` variables and refuses an address the renderer would
refuse. An items field is a row of its items, each opening its fields in a popover, with a plus that adds one. A
`choice` is a submenu of the block menu, a `toggle` a checkbox there, and a `number` a field in the block's settings
popover. Locked structure refuses a change to any of these fields, so the editor draws them read-only there; the
body still edits. `customBlocks` in `messages` words a
block's title and its fields, attributes and values by their names; the definition's labels stand in.

| Field                  | Holds                                                             |
| ---------------------- | ----------------------------------------------------------------- |
| `richText({ max })`    | bold, italic, links and variables; the block's body, at most one  |
| `plainText({ max })`   | one line of text and variables                                    |
| `link()`, `imageUrl()` | an address, or a url variable                                     |
| `lanes({ min, max })`  | lanes of other blocks side by side, as a columns block holds them |

| Attribute                       | Holds                            |
| ------------------------------- | -------------------------------- |
| `choice(values, default)`       | one of `values`                  |
| `toggle(default)`               | on or off                        |
| `number({ min, max, default })` | a number between `min` and `max` |

The primitives a `render` uses are on `h`: `section`, `columns`, `column`, `text`, `heading`, `button`, `image`,
`divider`, `list`, `code`, `table`, `icons`, `spacer` and `raw`. Each but `raw` takes a `class`. The renderer fills a primitive's
text and escapes it, so a variable's value never writes markup; `raw` takes HTML, as the HTML block does.
``h.raw`<td title="${subject}">` `` escapes every value it interpolates and never fills one, and fills each
`{{name}}` in its own text, escaped, in a block; `h.raw({ markup })` writes trusted markup as given, so in a
layout a person's value, such as the subject, never goes in it. A null or undefined value prints nothing; any
other value but text or a number throws `EmailMarkupInvalid`. Escaping keeps a value inside its attribute, but it
does not make a link safe: a `javascript:` address escapes to itself. So a link or an image goes through
`h.button`, `h.image` or a link in `h.text`'s markup, which check the scheme. A tagged `raw` takes a value in text,
in a comment, or in a quoted value of a plain attribute (`title`, `alt`, `class`, `width`, `data-*`, `aria-*` and
the like), and throws `EmailMarkupInvalid` for one anywhere else: an unquoted value, an attribute that takes a
link, a script or a style (`href`, `src`, `on*`, `style`), or inside a `style` or `script` element. It places the result in the block's own row, and writes the
plain-text twin from the same primitives. `defineEmailBlock` throws `BlockDefinitionInvalid` for a type
that is a default one or not a lower-case word, a field or attribute named `id`, `key` or `source`, two rich
text or lanes fields, or a default outside its attribute's values. Run `checkEmailRenderer(renderer,
{ layoutProps })` in a test: it renders each type's `sample` and lists what fails.

### Uploads

Given `upload`, the image block, a hero, a card, your blocks' `imageUrl` fields and each social icon get an Upload
tab beside their Link tab, and an image file pasted or dropped into the email becomes an image block that uploads
it. The email takes images only. Your answered address is checked as a typed one is: the image block, a hero, a
card and a social icon load over `https://` only, so an `http://` answer shows the error a typed one gets and the
block keeps the image it had.

```tsx
<EmailEditor profile={profile} value={blocks} label="Email body" onChange={setBlocks} upload={upload} />
```

[Editor Uploads](/docs/editor/editor-uploads) describes `upload`, the progress, the cancel and the retry.

### emailProfile

| Option       | Type                     | Default         |
| ------------ | ------------------------ | --------------- |
| `allow`      | `EmailBlockKind[]`       | every kind      |
| `variables`  | `VariableDeclaration[]`  | `[]`            |

| `blocks`     | `EmailBlockDefinition[]` | `[]`            |

`blocks` names your blocks from `defineEmailBlock`, and `validate` checks their fields. `extraKinds` names the

and `lanes` at their defaults, and a higher value throws `editor.profile.bound_above_renderer`. `blocks` and
`variables` may be raised.

| Bound       | Default | Limits                                          |
| ----------- | ------- | ----------------------------------------------- |
| `text`      | 5000    | characters of a paragraph, callout or list item |
| `label`     | 200     | characters of a button's label                  |
| `href`      | 2000    | characters of a button's link                   |
| `listItems` | 20      | items of a list                                 |
| `blocks`    | 50      | blocks in all, a lane's blocks included         |
| `lanes`     | 4       | lanes of a columns block                        |

## Variables

A variable has a `name` of word characters, a `type` of `string`, `duration`, `url` or `email`, and an
optional `label`, `sampleValue` and `required`. Type `{{` or use the toolbar's variable menu to insert one,
in text, in a button's label or in a link. The menu inserts into the label or the link field when that held
the focus before the menu. A token naming no declaration is drawn in red. A `required` variable that no block
uses is a problem.

A code block and an HTML block keep each token as its `{{name}}` text, so the export holds the text as typed.
The token is highlighted in place and drawn in red when nothing declares it, and typing `{{` there lists the
declarations to insert from.

The Link button in the toolbar or the selection bubble opens the link popover on the selected text, or on the
link the caret is in. A button's Link, in its block menu, opens the same popover on the button's link. Type
the link in its field, or click one of the `url` variables listed under it. A link is valid when it starts
with `https://`, `http://` or `mailto:`, or with a `url` variable. Any variable may follow, as in
`https://example.com/trip?token={{token}}`, and the renderer URL-encodes its value, so `mailto:{{email}}`
writes the address's `@` as `%40`, which mail clients read as `@`. A link that starts with a `url` variable
gets that value as it is, so the value supplies the scheme. In locked structure, or on a required button, a
button's link field is disabled, with the reason shown under it.

To change the variables, pass a new profile. If you change the declarations in place instead, call
`refreshVariables(editor)` from `variables/variable.tsx`.

## Validation

Each problem is marked on its block, with its message on hover and focus. A problem with no block, such as
`required-variable-not-printed` or `too-many-blocks`, and each problem the preview's render reports are listed
under the blocks. F8 and Shift+F8 move to the next and previous problem, and Escape on a marker returns
to its block.

On the server, `validate(blocks, profile)` from `@zeroxsolutions/editor-core/profiles/index` returns the same
list for the same profile, except `block-not-carried`. Only the editor reports that one, since it reads the
document before the export.

| Kind                            | Message                                                                 |
| ------------------------------- | ----------------------------------------------------------------------- |
| `variable-undeclared`           | This variable is not declared                                           |
| `href-invalid`                  | The link must start with https://, http://, mailto: or a link variable  |
| `link-invalid`                  | This link must start with https://, http://, mailto: or a link variable |
| `required-variable-not-printed` | A required variable is not used                                         |
| `markup-malformed`              | The formatting is not closed                                            |
| `block-not-allowed`             | This block is not allowed here                                          |
| `unknown-block-type`            | This block is of an unknown type                                        |
| `block-nested-too-deep`         | A block with lanes cannot sit inside a lane                             |
| `lanes-mismatch`                | The columns do not match their widths                                   |
| `lanes-count`                   | This block holds more or fewer lanes than it takes                      |
| `content-invalid`               | This block holds something its type does not read                       |
| `attributes-invalid`            | This block has a setting its type does not take                         |
| `text-empty`                    | This block is empty                                                     |
| `text-too-long`                 | This text is too long                                                   |
| `list-too-long`                 | This list has too many items                                            |
| `table-too-large`               | This table has more than 20 rows or 6 columns                           |
| `too-many-blocks`               | The email has too many blocks                                           |
| `block-not-carried`             | The email keeps only the text of this block                             |

`block-not-carried` marks a block the email cannot hold, such as a numbered list, a heading where the profile
holds none, or a table cell holding more than a line.
`content-invalid` marks content that is not an object, or a key its type's content does not have, which the
renderer's write check refuses; its `field` names the key. `attributes-invalid` marks attributes that are not
an object, or a key its type does not have or whose value it does not take, such as an `align` of `middle`; a
columns block's ratio is reported as `lanes-mismatch` instead.

## Markup

A paragraph, a callout and a list item store their text in this markup:

| Write                  | Reads as                                           |
| ---------------------- | -------------------------------------------------- |
| `**bold**`             | bold                                               |
| `_italic_`             | italic                                             |
| `[label](href)`        | a link to `href`, which may hold `{{name}}` tokens |
| `\*`, `\_`, `\[`, `\\` | the character itself, outside an href              |
| `\)`, `\\` in an href  | the character itself; any other `\` there is text  |
